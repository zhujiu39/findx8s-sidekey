## 实测事件

原始数据保存在 `side_key_events.txt`。采集命令为：

```sh
adb shell 'timeout 50 getevent -t /dev/input/event0'
```

50 秒到期后命令退出码为 124，这是本次设置的采集超时结束。普通 ADB shell（UID 2000）可以读取该输入节点，本次未申请 Root。

采集窗口内记录到三个完整的按下／松开事件对：

| 次序 | 按下时间（开机后秒数） | 松开时间（开机后秒数） | 持续时间 |
| --- | --- | --- | --- |
| 1 | 33123.319362 | 33123.475624 | 156.262 ms |
| 2 | 33124.178715 | 33124.295925 | 117.210 ms |
| 3 | 33125.085042 | 33126.717764 | 1632.722 ms |

日志开头还有一个未配对的松开事件，未用于时长计算。不能由这一轮记录推断用户所有操作均被捕获。

示例：

```text
[   33125.085042] 0001 02df 00000001
[   33126.717764] 0001 02df 00000000
```

第一行是按下，第二行是松开。中间的 `0000 0000 00000000` 为 SYN_REPORT 同步事件，不是另一个按键。

## 后续开发约束

- 通过输入设备名称 `gpio-keys`、支持的键码和设备路径识别目标，不将 `event0` 作为跨重启不变的编号。
- 监听 `type == EV_KEY && code == 735`，以值 1／0 维护按下状态并计算持续时间。
- 本次长按期间未观察到值 2 的内核重复事件。长按逻辑不能依赖收到重复事件，应根据按下时间判断；在松开时触发还是达到阈值时触发，等待用户确定。
- 735 是 Linux 输入键码。本次从实际使用的 Generic.kl 未找到 `key 735 ...` 显式映射，Android 框架层的厂商处理仍未核实，不能直接将 735 当作 `adb shell input keyevent` 的 Android 键码。
- `getevent` 读取不会独占输入设备；原功能如何处理、是否需要屏蔽，必须在明确功能需求后设计。
- 普通 shell 读取 `/sys/class/input/event0/device/name` 被拒绝，但 `getevent`、`dumpsys input` 和 `readlink` 已提供设备识别证据。

本次只完成按键识别，没有实施按键映射或拦截。短按、长按及双击的目标动作尚待用户指定。
