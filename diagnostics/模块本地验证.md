# 侧键自定义 v0.5.1 本地验证

日期：2026-09-21。本次聚焦 ColorOS 小窗启动；没有连接或操作目标手机。

## 问题依据与修正

用户提供的 v0.5.0 日志显示，小窗动作使用 `am start --windowingMode 5` 后得到 `Status: ok`，但实测没有进入小窗。这只能说明 Android 接受了启动，无法作为 ColorOS 小窗成功的依据。原来的全屏回退也不符合“只要小窗”的要求。

- 小窗分支改用 Root `app_process` 调用 `OplusZoomWindowManager.startZoomWindow`，传入明确桌面组件、当前用户与 OPlus 窗口模式。启动前核对接口签名、模式常量和状态结构。
- 从默认框架类路径加载 OPlus 接口；缺失时仅尝试系统只读目录中的 `oplus-framework.jar`。不打包厂商 JAR，不写死 Binder 事务号。
- 启动只提交一次；随后最多等待 4 秒，连续两次确认目标包名、目标用户、可见展开小窗及非空窗口区域。外层仍受脚本与原动作进程的总超时控制。
- 接口不兼容、返回错误、目标用户改变、状态超时、空状态或全屏状态均报告失败，不转为普通启动。Shell 层同时要求退出码为零和匹配目标应用／用户的小窗确认标记。
- 菜单应用统一以小窗打开，兼容旧配置的普通应用项。WebUI 移除菜单应用的打开方式选择；独立手势原先明确配置的普通启动动作继续保留。

适配依据：公开可读的 [OPlus 小窗管理接口](https://github.com/HBYShyw/AntiThermal/blob/main/oplus-framework/sources/com/oplus/zoomwindow/OplusZoomWindowManager.java)与[窗口状态结构](https://github.com/HBYShyw/AntiThermal/blob/main/oplus-framework/sources/com/oplus/zoomwindow/OplusZoomWindowInfo.java)。这些资料用于核对调用约定，不能代替目标 ROM 验证。

## 本地检查

- Java 编译及 D8 转换；独立状态测试覆盖延迟成功、错误包名／用户、全屏、隐藏小窗、空区域、瞬时状态、空状态、权限拒绝、启动拒绝、用户切换、4 秒边界和只提交一次。
- 反射接口测试检查签名、字段类型、窗口模式常量、参数传递与原始异常保留；不使用厂商框架实现作为本地测试替身。
- Shell 命令替身检查专用执行入口、组件和用户参数、日志管道、零退出码缺少确认标记不能算成功；超时、组件缺失和错误确认均不执行全屏回退。
- 普通手势应用启动的显式入口、当前用户和错误检查回归；22 项 JavaScript 测试，包括旧应用项批量选择后统一小窗。
- 原有 C／Java 测试、2048 应用配置与分块保存、菜单几何、安装脚本和 Shell 语法检查；ARM64 静态 ELF、16 KiB 对齐、API 35 菜单 APK、v3 签名和版本 51 校验。

完整构建入口为 `python build.py`，本次输出位于独立的 `test_v0.5.1_ColorOS仅小窗启动修复` 交付目录。应用目录入口仍有既有过时 API 编译提示，菜单 APK 编译使用 `-Werror`。

## 实机待验

本地替身测试只确认调用约定和失败处理，不能证明目标 ColorOS 15 的小窗接口、权限策略和应用支持已通过。刷入并重启后确认菜单组件版本为 v0.5.1，再从菜单打开应用。

“应用启动”日志应出现 `OplusZoomWindowManager.startZoomWindow`。只有最后出现“系统已确认目标应用进入 ColorOS 小窗”才算本次状态确认成功；报错时保留具体异常、启动返回码或最后小窗状态，不能仅凭动作触发或 `Status: ok` 判断通过。
